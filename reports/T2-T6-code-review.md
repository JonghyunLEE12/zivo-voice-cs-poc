### 6. 중간 - zh-TW/yue '兩' 규칙이 두 자리 수를 망가뜨린다
- 위치: `server/normalize/num_zh.py:35-36`, `:11-14`
- 왜 문제인가: 실측 `12個人，22人，2點` → `十兩個人，二十兩人，二點`. 규칙 `二(?=小時|分鐘|晚|人|個)`가 앞 글자를 보지 않아 '十二', '二十二'의 끝 '二'까지 '兩'으로 바꾼다. 시각 '2點'은 대만에서 보통 '兩點'인데 바뀌지 않는다. yue는 이 규칙에서 빠져 `2個人` → `二個人`이 된다(광둥어는 '兩個').
- 어떻게 고칠까: 숫자 토큰 단위로 처리한다. 원래 아라비아 숫자 값이 정확히 2일 때만, 양사·'點' 앞에서 '兩'을 쓰도록 NUMBER 치환 콜백 안에서 뒤 문자를 보고 결정한다. yue에도 같은 규칙을 적용한다. `12個`, `22人`, `2點`, `2:00` 테스트를 추가한다.

### 12. 낮음 - tool_call 병합 시 index 없는 여러 청크가 하나로 합쳐질 수 있다

- 왜 문제인가: index가 없으면 청크 안의 위치(`position`)를 쓰기 때문에, 서로 다른 청크로 온 두 호출이 모두 0번이 되어 이름이 `lookup_reservationget_cancellation_policy`처럼 이어 붙고 인자가 섞인다. Ollama 0.33이 매번 index를 보내는지는 확인하지 못했다. 단위 테스트는 index가 있는 경우만 다룬다(tests/test_llm.py:90-91). `tool.detected`의 name이 빈 문자열일 수 있다.
- 어떻게 고칠까: Ollama 네이티브 스트림은 tool_call을 완성된 형태로 보내므로, index가 없으면 '새 호출'로 append하고 이름 연결 로직은 없앤다. 병합된 결과의 이름이 TOOLS에 없으면 실패로 처리한다.

### 13. 낮음 - 코드 파서가 'oh'(0)를 모르고 접두어 없는 코드를 거절한다
- 위치: `server/normalize/codes.py:6-14`
- 왜 문제인가: 실측 `'Z V four oh two one'` → None, `'4821'` → None. 영어 화자는 0을 'oh'로 많이 말한다. 모델이 사용자가 말한 숫자만 인자로 넘기면 `invalid_reservation_code`가 되고, 이것은 실패 카운트에도 들어가지 않아 같은 질문이 반복될 수 있다.
- 어떻게 고칠까: en에서 접두어 뒤 문맥에 한해 `oh`/`o`를 0으로 받는다. 4자리 숫자만 왔을 때는 'ZV-' 확인 질문을 하라는 오류 메시지(`expected_prefix`)를 돌려준다.

### 14. 낮음 - yue 출력에 문자체계 변환이 없다
- 위치: `server/llm/ollama_client.py:24`
- 왜 문제인가: yue는 번체가 규칙이지만 CONVERTERS에 없어 모델이 간체를 섞으면 그대로 나간다. 시나리오 테스트에도 yue가 없다.
- 어떻게 고칠까: `OpenCC('s2hk')`를 추가하고 yue 시나리오 1세트를 넣는다.

### 15. 낮음 - 스키마와 구현의 사소한 불일치
- 위치: `server/llm/tool_schemas.json:8-13,22-27,37-42`, `server/llm/tools.py:33`
- 왜 문제인가: 구현은 추가 키가 하나라도 있으면 거절하는데(`set(arguments) != required`), 스키마에는 `additionalProperties: false`가 없어 모델이 알 방법이 없다. `summary_ko`가 한국어인지는 서버가 검증하지 않는다(시나리오 검사기만 확인). 오류 응답의 `required`에 `list(props)`를 넣고 있어 이름과 내용이 다르다.
- 어떻게 고칠까: 스키마에 `additionalProperties: false`를 넣는다. `summary_ko`에 한글 포함 여부를 검사하고, 실패하면 `invalid_summary_ko`를 돌려준다. 오류 필드는 `schema['parameters']['required']`로 바꾼다.

### 16. 낮음 - 수수료 내림과 날짜 경계 의미가 문서화되지 않았다
- 위치: `server/llm/fake_db.py:50-61`
- 왜 문제인가: `fee_krw = total * fee // 100`은 내림이라 고객에게 유리하다. 현재 데이터에서는 나누어떨어져 문제가 없다. 호텔 `free_days_before: 3`은 '체크인 3일 전 날짜의 끝까지 무료'로 구현됐다(포함). 실제 정책 문구와 맞는지는 설계서 기준 확인이 필요하다.
- 어떻게 고칠까: 반올림 규칙과 경계 의미를 policies.json에 명시하고(`rounding`, `deadline_inclusive_end_of_day`), 나누어떨어지지 않는 금액 테스트를 1개 추가한다.

## 확인했지만 문제 없던 것

- 성 불일치와 없는 코드는 같은 응답이며, 예약 정보가 새지 않는다. 같은 코드의 성 검증이 실패하면 권한도 제거한다.
- `get_cancellation_policy`는 lookup 성공 전에는 `lookup_required`를 돌려준다.
- 데모 날짜 기준 5건의 수수료·환불 금액은 보고서 표와 일치한다(ZV-4821 50%/143,000).
- en/zh 금액·퍼센트·코드(앞자리 0 보존) 정규화, ja의 월·일 특수 독음, zh 오후 시각 12시간제 변환은 정상이다.
- 스트림 취소 시 HTTP 연결이 닫히는 테스트가 있고, 원격 엔드포인트는 거부한다.
