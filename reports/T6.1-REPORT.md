`llm.delta`는 도구 사용 가능 라운드의 **done 프레임을 확인한 뒤** 문장별로 나온다. 첫 문장만 잠깐 버퍼링하면 뒤늦은 도구 호출을 되돌릴 수 없으므로 전체 최종 라운드를 보류했다. 첫 문장 지연 증가분을 숨기지 않고 별도 측정하며, 즉시 토큰을 읽어 TTS를 시작하는 방식은 아니다.

`commit_spoken`은 스트림 consumer의 취소를 await하거나 generator를 aclose한 뒤, 실제 재생 시작된 `llm.delta` 문장들의 정확한 접두부를 전달한다. 완료된 턴이면 도구 쌍을 보존하고 assistant만 줄이며, 중단된 턴이면 롤백 상태에서 user+재생 문장만 남긴다. 빈 문자열은 해당 턴 전체와 가짜 도구 상태를 되돌린다. 이 PoC에는 외부에 실재하는 handoff 부작용이 없으며, 실서비스 전환에서는 실제 부작용에 별도 조정이 필요하다.

현재 턴에 명시된 성만 파싱하며 DB에서 성을 추측하지 않는다. 누락/복수/모호한 성이나 예외·상담원 요청은 모델 경로를 유지한다. 이전 턴에서 말한 성을 server prefetch에 합치는 확장은 하지 않았다.

### 첫 토큰 / 첫 문장 전후 비교

단위 ms, 각 칸 3회 중앙값. 워밍업 후 요청 시작 기준이며 로드 시간은 제외한다. **수정 전 구현 snapshot과 수정 후 구현에 같은 최종 프롬프트·현재 도구/DB·8192 context를 적용한 통제 비교**다. 과거 T6 전체 환경을 그대로 재현한 값이 아니다. 반복마다 전후 실행 순서를 번갈아 캐시 순서 편향을 줄였다. 이전 구현의 첫 문장은 llm.delta를 누적해 첫 종결부호가 도착한 시각, 이후는 실제 문장 이벤트 도착 시각이다.

**영어 조회·취소만 전후 모두 품질 검사 3/3을 통과해 성능 비교가 유효하다.** 영어 조회 첫 토큰은 3,092.3→1,578.6ms, 첫 문장은 4,164.9→2,594.9ms; 취소 첫 토큰은 4,077.6→1,904.3ms, 첫 문장은 4,628.5→2,517.1ms다. 나머지 수정 전 표본은 도구 누락/잘못된 정책/사전 발화로 인한 길이 위반 등이 있어 짧은 응답을 성능 성공으로 보지 않는다. 원문과 검사 사유는 `latency.json`에 모두 보존했다.

수정 후 측정 24/24는 품질 검사 통과, 전부 1라운드다. 전체 수정 후 첫 토큰 중앙값은 1,571.8ms, 첫 문장은 2,410.2ms다. 여전히 첫 토큰 1초 목표를 초과한다. 9b 선택의 판단 자료로만 제공하며 다운로드하지 않았다.

기존 `reports/T2-T6-REPORT.md`의 첫 토큰 중앙값은 en 3495.4 / zh-CN 3982.4 / zh-TW 3790.0 / ja 3661.9ms였다. 당시 첫 문장 시각은 저장되지 않아 그 값과의 완전한 전후 비교는 불가능하다. 과거 수치를 첫 문장 수치로 대체하지 않았다.

라운드별 `load_duration`, `prompt_eval_count/duration`, `eval_count/duration`, `total_duration`은 Ollama 원래 단위(ns/count)로 저장하며, `elapsed_ms`는 별도 wall-clock이다. 빈 messages 워밍업 응답은 `done_reason=load`만 주고 duration을 반환하지 않아 워밍업 자체의 지연값은 주장하지 않는다.

## 남은 실패와 판단

요청된 코드 수정·pytest·실제 검증·보고서 완료 기준은 수행했다. 다만 최종 모델의 상담원 도구 호출 및 일부 다회차 도구 선택은 실패하므로 T9 품질 준비 완료 판정은 보류해야 한다. 추가적인 서버 intent 라우팅/전환 강제나 다른 모델 검증은 이번 지정된 코드 리뷰 범위를 넘어 별도 결정이 필요하다. 테스트를 느슨하게 하거나 실패 응답을 바꿔 PASS로 만들지 않았다.

## 설계·메모리 제약

- 새 모델 다운로드 0건. 기존 `qwen3.5:35b-a3b`(Q4_K_M, API의 parameter_size 36.0B)만 사용. 9b 미다운로드, 모델 파일 변경 없음, 유료 API/키/외부 게시 없음.
- TTS 서버를 시작하지 않았다. 코디네이터가 모델 창을 배정한 뒤 Ollama만 사용하고 각 검증 스크립트의 finally에서 언로드했다.
- 최초 절대 swap 21.3GiB로 보류 → 코디네이터가 시작 대비 증가량으로 변경 → free%14로 두 차례 자동 중단·언로드 → pressure warn30초로 세 번째 중단 → 최종 코디네이터 기준은 **critical(4), swap 시작 대비 +4GiB 초과, 디스크10GiB 미만**만 중단이다. warn(2)/free%는 관찰만 한다. 지시 메시지 ID와 이유는 `docs/DEVIATIONS.md`에 남겼다.
- 자원 샘플 387건에서 최대 swap 증가 1,790.19MiB, 최소 디스크 여유 133.90GiB였고 관찰된 pressure는 normal(1)/warn(2)뿐이었다; critical(4)는 없었다. 마지막 `ollama stop qwen3.5:35b-a3b` 후 `/api/ps`의 `models:[]`를 확인하고 모델 창을 T7 워커에게 반환했다.
- `scripts/llm_resources.py`는 모델 요청 전과 요청 중 5초마다 검사한다. 초기 중단 원자료와 최종 샘플을 `reports/t6_1/resources.jsonl`에 함께 보존했다.
- 초기 중단과 중간 프롬프트의 실패 결과도 `scenarios-partial.*`, `scenarios.*`에 보존했다. 중간 cooldown 방식을 종료하기 위한 프로세스 SIGINT 1회는 결과 성공으로 세지 않았다.

## 범위 밖으로 남긴 리뷰 항목

4턴 제한은 토큰 단위 한도가 아니다. 매우 긴 단일 입력/턴은 8192 context를 넘을 수 있으므로 T9의 입력 제한은 별도 필요하다. 한국어 고유명사·언어 자연스러움·억양은 이 텍스트 휴리스틱 검사로 보증하지 않는다.
